## 1. Запуск контейнера

```bash
docker run -d -p 8080:8000 --name pyserver python:3-alpine python -m http.server 8000
```

**Результат:**
```
191e70a6bff3c928caefee873b75088908836963c7fb456cdf07df9a68c4d966
```

**Пояснення:**
- `docker run -d` — запускає контейнер у фоновому (detached) режимі
- `-p 8080:8000` — пробрасує порт: запити на порт `8080` хоста перенаправляються на порт `8000` всередині контейнера
- `--name pyserver` — задає ім'я контейнеру для зручності
- `python:3-alpine` — образ Python на базі Alpine Linux (мінімальний, ~18 МБ)
- `python -m http.server 8000` — запускає вбудований HTTP-сервер Python на порту 8000
- Docker повертає повний ID контейнера — підтвердження успішного запуску

## 2. Процес всередині контейнера — PID 1

```bash
docker exec pyserver ps aux
```

**Результат:**
```
PID   USER     TIME  COMMAND
    1 root      0:07 python -m http.server 8000
    7 root      0:00 ps aux
```

**Пояснення:**

PID 1 всередині контейнера — це `python -m http.server 8000`.

Контейнер — це не окрема віртуальна машина, а **ізольований Linux-процес**. Docker використовує `namespace` ізоляцію, тому всередині контейнера процеси мають власний простір PID, що починається з 1. Перший запущений процес завжди отримує PID 1 — в нашому випадку це саме Python HTTP-сервер, оскільки він був вказаний у команді `docker run` як основна команда.

**Ключова ідея:** контейнер живе рівно стільки, скільки живе його PID 1. Якщо цей процес завершується — контейнер зупиняється автоматично.

## 3. Перевірка доступності сервісу

```bash
curl http://localhost:8080
```

**Результат:**
```html
<!DOCTYPE HTML>
<html lang="en">
<head>
<title>Directory listing for /</title>
...
<h1>Directory listing for /</h1>
```

**Пояснення:**
- `curl` надіслав HTTP GET-запит на порт `8080` хоста
- Docker перенаправив його на порт `8000` всередині контейнера через port mapping
- Python HTTP-сервер відповів списком директорій кореневої файлової системи контейнера — видно стандартні директорії Alpine Linux (`/bin`, `/etc`, `/usr` тощо)

## 4. Логи контейнера

```bash
docker logs pyserver
```

**Результат:**
```
172.17.0.1 - - [20/Jun/2026 08:43:34] "GET / HTTP/1.1" 200 -
```

**Пояснення:**

Docker перехоплює **stdout** та **stderr** процесу PID 1 і зберігає їх як логи контейнера. Python HTTP-сервер виводить кожен запит у stdout — саме тому `docker logs` показує HTTP-запит від `curl`.

`172.17.0.1` — це IP-адреса шлюзу мережі Docker (docker0 bridge), тобто трафік прийшов з хост-машини через внутрішню мережу Docker.

Логи доступні навіть після зупинки контейнера, оскільки Docker зберігає їх окремо від процесу.

![Логи контейнера](assets/container_logs.avif)

## 5. Зупинка контейнера

```bash
docker stop pyserver
docker logs pyserver
```

**Результат:**
```
pyserver
172.17.0.1 - - [20/Jun/2026 08:43:34] "GET / HTTP/1.1" 200 -
```

**Пояснення:**

`docker stop` надсилає процесу PID 1 сигнал **SIGTERM** (сигнал №15) — це "м'яке" завершення, що дає процесу час коректно завершити роботу (закрити з'єднання, зберегти стан).

Якщо процес не завершується протягом 10 секунд (timeout за замовчуванням) — Docker надсилає **SIGKILL** (сигнал №9), який неможливо ігнорувати і який примусово вбиває процес. Саме тому в `docker ps -a` видно код завершення `Exited (137)` — це означає що процес отримав SIGKILL (128 + 9 = 137).

Логи залишаються доступними після зупинки.

![Зупинка контейнера](assets/container_stop.avif)

## 6. Перевірка статусу контейнера

```bash
docker ps -a
```

**Результат:**
```
CONTAINER ID   IMAGE            COMMAND                  STATUS
191e70a6bff3   python:3-alpine  "python -m http.serv…"   Exited (137) About a minute ago   pyserver
```

**Пояснення:**
- `docker ps -a` — показує всі контейнери, включаючи зупинені (`-a` = all)
- `Exited (137)` — контейнер завершився з кодом 137 (SIGKILL: 128 + 9)
- Контейнер зупинився тому що завершився його PID 1 — Python HTTP-сервер
- Стан контейнера зберігається і його можна перезапустити командою `docker start pyserver`

## Висновки

**Контейнер = процес + ізоляція.** Docker не створює окрему віртуальну машину — він запускає звичайний Linux-процес в ізольованому середовищі за допомогою namespace та cgroups.

**Що визначає життя контейнера:** контейнер існує рівно стільки, скільки існує його PID 1. Завершення головного процесу = завершення контейнера.

**Сигнали завершення:**
- `docker stop` → спочатку **SIGTERM** (м'яке завершення, процес може прибратись)
- якщо процес не реагує за 10 секунд → **SIGKILL** (примусове вбивство, ігнорувати неможливо)

**Логи:** Docker збирає stdout/stderr PID 1 і зберігає їх незалежно від стану контейнера — саме тому `docker logs` працює навіть після зупинки.
